# Gap check of research/website_plan.md

Status: review only (2026-10-03). Nothing was built and `website_plan.md` was not edited. Every data figure below was read from `data/budget.db` (file dated 2026-10-02 17:40, `checks.run_at` 2026-10-02T22:40Z) with the SQL or Python shown. "Plan" means `research/website_plan.md` at commit `520d217`.

## Verdict

**The plan is sound in shape and close to buildable, but it is not ready to hand to a developer as written.** Four things would make the first build fail or make the site say something untrue, and all four are cheap to fix in the plan:

1. **The validator forbids the string `raw/` in any export, but 24,596 box sources and 2,235 side fact sources carry a `file: raw/...` path.** As written, `validate_site_data.py` fails on the first run. The plan has to choose: strip `file` from the export, or relax the check.
2. **The coverage figures are labelled backwards.** The plan says 42.2% / 14.2% / 43.7% (City) are "the strict figures by each leaf's own amount" and that `build/README.md` prints a looser build rule. It is the other way round. `checks.depth` is computed by `treelib.depth_report`, which counts every count x rate leaf as under $1M. The strict figures are City 9.6% / 20.8% / 69.5%, CPS 21.0% / 35.6% / 43.4%, Parks 32.8% / 41.5% / 25.7%. Audit 3 says the same (strict City 69.5% at $10M or more). The front page sentence "42 cents of every City dollar reach a box under $1M" would be wrong under the rule the plan says it uses.
3. **One cut-off date is stamped on every "Paid so far" box, but 78 `paid_to_date` boxes are not January 1 to September 28, 2026.** 16 City settlement boxes come from the Law Department report through 2026-07-31. 50 CPS boxes are fiscal year 2026 (July 2025 to June 2026) supplier totals that CPS does not tie to budget lines. 12 CPS capital boxes are FY2026 project spending. The basis badge text and the manifest's single cut-off would invent a date for them. Side facts have the same problem: `vendor_payment` (listed under "Paid so far in 2026") is Parks 2019 to 2022 and CPS FY2026.
4. **The job-title privacy rule is too narrow.** The plan strips `pay_2025` rows where `n_paid_2025 < 5` or `n_current < 5` and counts 165 such rows. There are 381 (165 by 2025 count, 350 by current count). A further 52 rows pass both tests but carry a 2024 total for a group of 1 to 4 people (`n_paid_2024 < 5`). The fields are nested under `extra.group`, which the plan does not say. If the rule ships as written, pay totals for groups under 5 reach the site.

Beyond those, the main engineering gaps are: the spine is 396 KB gzipped if it carries side facts as the plan says (budget 100 KB); the largest chunk is 148 KB gzipped at every cut threshold tried (150, 200 and 300 boxes), so "cut at 200" does not buy the headroom the plan expects; breadcrumb names for boxes deeper than depth 3 are not in the spine; the "N positions x $R each" formula is wrong for 1,990 boxes; 5 negative parents, 2 zero-amount parents and 303 one-child boxes whose only child is a leaf break the stated tile and collapse rules; and 79 ids are longer than 255 characters, which breaks static file names for 2 pre-rendered pages. The Cloudflare Pages 20,000 file limit is already exceeded by the plan's own numbers (10,656 pre-rendered pages plus 9,120 per-box JSON before chunks, search, vendors and assets).

The requirements are nearly all handled somewhere in the plan (traceability table below). The weak spots are the three above (honesty of coverage, "never invent numbers" for dates, and the under-5 rule) plus one privacy edge: individuals' payment descriptions are passed through and 118 of them still carry role words and name fragments ("Poet Laurate", "Jr", a middle initial) that could re-identify a person.

## Engineering notes not tied to one data fact

- **Stack (Astro plus Svelte islands):** reasonable. One risk not listed: Astro pre-rendering 10,656 pages that each need a chunk lookup is fast only if the export is loaded once into memory in a build-time module, not re-read per page. Say so.
- **Deep link to a renamed id:** the nearest-ancestor rule works because every id's parent is its prefix (verified). The client needs the chunk index to know which prefix exists; the manifest covers it. Fine.
- **Search index privacy:** the index is built from exported JSON, so it inherits the privacy rules. Add one explicit check: no index entry has `is_individual` or a name containing "name hidden" (individuals should not be searchable at all).
- **Validator order:** `validate_site_data.py` should run after `npm run build` too (the plan runs it before) so that the `dist/` em dash and path checks see the final HTML, not only the JSON. The leak check covers names but not em dashes.
- **Service worker (open question 10):** if added, it must be versioned by the build hash or stale chunks will show old amounts next to a new manifest after a refresh.
- **Update flow:** the plan says the cut-off date "changes on every page automatically". That is only true if no content file hard-codes it (13.5 covers it) and if gap 3 is fixed so that a refresh does not re-stamp the Law Department and CPS boxes with the new date.
- **Hosting file count:** see gap 13. Also confirm Cloudflare Pages' 25 MB per-file limit is not an issue (largest file is a chunk under 3 MB raw).
- **Acceptance criteria:** M2 "Lighthouse performance 90 on a depth 8 box" is measurable. M3 "snapshot set approved" and M5 "glossary covers every word flagged" depend on the kid test rehearsal that is scheduled in M7; move the rehearsal to M5.
